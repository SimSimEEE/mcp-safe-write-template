# How harness-engine is applied here

[harness-engine](https://github.com/SimSimEEE/harness-engine) (Apache-2.0) is a commit/PR quality gate for
Claude Code. This folder is the **overlay** that adapts it to this repository. Nothing from the engine is
vendored: `setup.sh` fetches the pinned commit.

## Files

| Path | Tracked | What it is |
|---|---|---|
| `ENGINE_PIN` | yes | `version=` (engine `ENGINE_VERSION`) and `commit=` (40-char sha) to install |
| `setup.sh` | yes | turn the layer on (fetch the pinned engine, lay it out under `.claude/`) or off (`--remove`) |
| `hook.sh` | yes | wrapper that `.claude/settings.json` calls for each engine hook |
| `categories/ts-mcp-server/` | yes | overlay category: how the engine recognises and tests this repo |
| `profiles/simsimeee/mcp-safe-write-template.json` | yes | pins this repo to that category (made by the engine's `profile.sh`) |
| `agents/test-runner.md` | yes | engine agent with jest replaced by vitest |
| `agents/test-runner.base.sha256` | yes | sha256 of the engine file the override was derived from |
| `../harness-engine/` | no | engine checkout at the pinned commit |
| `../agents/`, `../skills/`, `../hooks/` | no | engine copy + overlay agents, generated by `setup.sh` |

## Turning it on and off

The Claude Code layer is **opt-in**. Until it is turned on, the hooks in `.claude/settings.json` do nothing
and only the base layer (git hooks + CI) gates commits.

```bash
npm run harness:setup
```

```bash
npm run harness:off
```

Turn it on once per checkout (again after changing `ENGINE_PIN`). Nothing turns it on automatically, not
even in Claude Code cloud sessions: every gated commit starts several review agents, so whether to pay
that cost is a per-checkout decision. A cloud session that wants the gate runs `npm run harness:setup`
first; each cloud session starts in a fresh container, so it is off again in the next one.

## Where the engine's install method did not fit, and what was done instead

| Engine default | Problem for this repo | Adaptation |
|---|---|---|
| `install.sh` installs into `~/.claude` (user scope) and merges hooks into `~/.claude/settings.json` | The template must be self-contained: cloud sessions, forks for client projects, people who do not use the engine elsewhere. Writing to someone's home directory on clone is not acceptable. | `setup.sh` lays the engine out in the **project** `.claude/` folder, in git-ignored directories. The engine's scripts locate themselves relative to their own folder (`PF_ROOT` = parent of `hooks/`), so the same layout works at project scope. Only the observation log (`PF_LOG`) still goes to `~/.claude/preflight-log.jsonl`; it does not affect any decision. |
| Hooks are registered with `$HOME/.claude/hooks/...` paths | Project hooks must work before the engine is set up and must not run twice when someone also has the engine installed user-wide. | `.claude/settings.json` calls `hook.sh <name>`. It runs `.claude/hooks/<name>` if present; otherwise it does nothing, which is what keeps the layer opt-in. If `~/.claude/settings.json` already registers the same hook, it steps aside. |
| Overlay is a separate repository passed with `install.sh --overlay` | One more repository to keep in sync for a single template. | This folder **is** the overlay (`categories/`, `profiles/`, `agents/`). `setup.sh` writes its path into the copied `skills/preflight/config.json` as `overlayDir`. |
| Overlays pin the engine in a pin file (`version`, `commit`) and installation fails on a version mismatch | — (fits as is) | `ENGINE_PIN` uses the same two lines. `setup.sh` refuses to continue if `ENGINE_VERSION` at the pinned commit differs from `version=` (fail closed, as the engine does). |
| `test-runner` lane runs `eslint` + `tsc --noEmit` + **jest** | This repo uses vitest. | `agents/test-runner.md` overrides the engine agent (same name wins, as with `install.sh`): only the jest steps and wording changed. `setup.sh` warns if the engine's original changes (sha256 drift), so the override does not silently fall behind. |
| Categories `shell-tool` / `generic` | `generic` has no regression commands, so the test-runner lane would have nothing concrete to run. | Overlay category `ts-mcp-server` matches on `package.json`, `vitest.config.ts`, `scripts/mutation-check.mjs`, `scripts/secret-scan.mjs`, and returns regression commands: `npx vitest run`, `node scripts/secret-scan.mjs --all`, and `node scripts/mutation-check.mjs` when `src/` or `tests/` change. It also marks `config/keys.json` as a sensitive path. |
| Knowledge-vault lanes (`vault-linter`, `vault-sync`), dev-deploy QA lanes | This repo has no vault and no deployed dev environment. | `vaultDir` is left empty; the category defines no QA rules, so the engine records those lanes as not applicable. |

## Verified in this repository

- `setup.sh` fetched the pinned commit, laid out `.claude/`, and the engine's own loader classified this repo
  as `ts-mcp-server` with the profile above.
- A classification of a staged change selected `secret-scanner`, `test-runner` and `crossrepo-impact`, with
  the regression commands from the category.
- Fed a `PreToolUse` payload for a commit with no gate record, `hook.sh preflight-gate.sh` returned
  `permissionDecision: deny`; for `ls` it allowed; with the engine absent it allowed with a warning.
- In a live Claude Code session the project hooks took effect as soon as `.claude/settings.json` existed.
- In a fresh clone: before setup the commit hook allowed silently; after `harness:setup` it denied an ungated
  commit; after `harness:off` it allowed silently again.

## Known behaviour worth knowing

- The commit gate matches commit commands inside any Bash command text, including heredocs that merely
  *mention* one. Write such text with the editor tools rather than shell heredocs. This is engine behaviour,
  kept as is (it errs on the safe side).
- The full `/preflight` run orchestrates several agents and costs tokens accordingly. When no lane is
  selected, `skills/preflight/preflight-fast.sh <repo> commit` records the pass without running agents.

## Updating the engine

1. Pick the new engine commit (normally a merge commit on its `main`) and its `ENGINE_VERSION`.
2. Update both lines of `ENGINE_PIN`.
3. `npm run harness:setup`; if it warns about `test-runner.md`, re-apply the jest→vitest diff to
   `agents/test-runner.md` and update `agents/test-runner.base.sha256`.
4. If the engine's profile format changed, recreate the profile with `.claude/skills/preflight/profile.sh init`.
